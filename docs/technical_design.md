# Technical Design

## Цель

Построить Telegram-бота, который собирает ежедневные статусы по задачам команды и синхронизирует их с Odoo. Бот должен быть полезен участнику, PM и техлиду, но не должен подменять полноценные ретро или планирование.

## Архитектура

```text
Telegram
   |
   | webhook / polling
   v
FastAPI + aiogram
   |
   | business services
   v
PostgreSQL <---- scheduler / worker
   |
   | Odoo adapter
   v
Odoo
   |
   | task assignment webhook or polling
   v
FastAPI endpoint

AI provider вызывается только для US3, когда участник явно отметил затруднение.
```

## Основные модули

- `bot`: Telegram handlers, FSM, inline-кнопки.
- `odoo_client`: чтение задач, обновление статусов, запись комментариев.
- `daily_service`: ежедневный цикл по задачам и upsert ответа за день.
- `weekly_service`: выбор фокуса недели.
- `blocker_service`: создание затруднения, AI-совет, снятие, эскалация.
- `digest_service`: дневные и недельные дайджесты PM.
- `outbox_service`: надёжная доставка в Odoo при временных ошибках.
- `scheduler`: задачи по расписанию в часовом поясе `Asia/Yekaterinburg`.
- `db`: SQLAlchemy-модели истории и фабрика асинхронных сессий.

## Данные

Минимальные таблицы:

- `users`: Telegram user id, Odoo user id, роль, активность.
- `task_cache`: локальный снимок Odoo-задач для быстрых сообщений и истории.
- `daily_answers`: один ответ на пару `user + task + date`; уникальный индекс.
- `daily_summaries`: завершение дейли и общий текст вне списка задач, один на день.
- `weekly_plans`: фокус задач на неделю.
- `blockers`: открытые/решённые/эскалированные затруднения.
- `ai_advices`: текст рекомендации, задача, затруднение, дата.
- `odoo_outbox`: операции, которые надо повторить при сбое Odoo.
- `pm_digest_runs`: история отправленных дайджестов.

## Интеграция с Odoo

Первый шаг после получения доступов:

1. Вызвать `/web/version`.
2. Определить API style:
   - текущие test/prod стенды: Odoo 18, используем XML-RPC.
   - Odoo 19+ в будущем: `/json/2`.
3. Через API или developer mode выяснить:
   - техническую модель задачи: скорее всего `project.task`;
   - поле исполнителей: скорее всего `user_ids`;
   - поле статуса: `stage_id` или кастомное поле;
   - поле дедлайна: `date_deadline`;
   - способ ссылки на карточку: `access_url` или формирование URL по action/model/id.
4. Проверить запись в chatter через `message_post`.
5. Проверить, можно ли добавлять кастомные поля вроде `x_result_url`, `x_blocker_status`.

## Odoo outbox

Любая запись в Odoo сначала фиксируется локально:

1. Telegram-ответ сохраняется в PostgreSQL.
2. Создаётся запись `odoo_outbox`.
3. Worker пытается отправить операцию в Odoo.
4. При 5xx/timeout операция остаётся в очереди и повторяется с backoff.
5. При 4xx ошибка помечается как failed и попадает в админский лог.

Так ответ участника не теряется, даже если Odoo временно недоступна.
Ключ идемпотентности не позволяет повторному Telegram update создать вторую
операцию синхронизации. Интервалы повторов растут от 15 секунд до одного часа.

## Telegram UX

Ежедневный цикл:

1. Бот получает открытые задачи пользователя.
2. По каждой задаче спрашивает прогресс.
3. Показывает кнопки статусов из Odoo.
4. Показывает кнопки `Есть затруднение`, `Пропустить`, `Пропустить остальные`.
5. Если выбран статус `Готово`, спрашивает ссылку на результат.
6. После задач задаёт общий вопрос: `Делал что-то ещё, не из списка?`

Недельное планирование:

1. В понедельник перед дейли бот показывает список открытых задач.
2. Пользователь выбирает фокус недели кнопками.
3. Потом может добавить стратегический текст вне задач.

## AI-совет

Контекст для модели:

- название задачи;
- проект;
- дедлайн;
- текущий статус;
- сколько дней задача в текущем статусе;
- текст затруднения;
- недавние обновления именно по этой задаче.

Контракт ответа:

```json
{
  "recommendation": "короткий следующий шаг",
  "clarification_question": null
}
```

Если данных недостаточно:

```json
{
  "recommendation": "",
  "clarification_question": "один уточняющий вопрос"
}
```

## Расписание

Часовой пояс: `Asia/Yekaterinburg`.

- 09:00 Пн: недельное планирование.
- 10:00 Пн-Пт: дайджест PM за предыдущий рабочий день.
- 12:00 Пн-Пт: daily cycle.
- 14:00 Пн-Пт: напоминание неответившим.
- 18:00 Пн-Пт: проверка эскалаций.

## Роли

- Участник: отвечает по своим задачам и видит AI-совет.
- PM: видит дайджесты, эскалации и команды по людям/задачам.
- Техлид: получает тот же уровень информации, что PM.

Тексты затруднений не рассылаются всей команде и по умолчанию не пишутся в общий
chatter Odoo. В карточке задачи остаётся рекомендация, а полный текст доступен автору,
PM и техлиду в Telegram. Изменение этого режима требует явной настройки
`ODOO_INCLUDE_BLOCKER_TEXT=true` и согласования с командой.
