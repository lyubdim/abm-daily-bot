# E2E Test Plan

## Цель

Подтвердить полный путь данных между Telegram, PostgreSQL и test Odoo до включения
production-доступа. Все проверки выполняются на отдельном проекте и задаче
`ABM Daily Bot Test`; реальные задачи команды не изменяются.

## Предусловия

- Docker Desktop показывает `Engine running`.
- Локальный `.env` заполнен тестовыми секретами и не отслеживается Git.
- `DEMO_MODE=false`, тестовый Odoo user ID настроен.
- В Odoo существует открытая задача, назначенная тестовому пользователю.
- Последний GitHub Actions CI завершился успешно.

## TC-01: запуск и регистрация

1. Запустить `scripts/start-test.cmd`.
2. Убедиться, что `postgres` имеет состояние healthy, а `bot` - running.
3. Отправить боту `/start`.

Ожидается: бот показывает команды, пользователь появляется в таблице `users`, секреты
не выводятся в логи.

## TC-02: ежедневный статус

1. Отправить `/daily`.
2. Проверить название, проект, дедлайн, статус и ссылку тестовой задачи.
3. Ввести прогресс и явно выбрать новый статус кнопкой.
4. Завершить задачи и ответить на общий вопрос вне списка.

Ожидается: одна строка появляется в `daily_answers`; статус меняется в Odoo; в chatter
появляется комментарий `[ABM Daily Bot]` с прогрессом; создаётся одна
`daily_summaries` с общим ответом.

## TC-03: повторный ответ за день

1. Снова пройти `/daily` для той же задачи.
2. Ввести другой прогресс и выбрать статус.

Ожидается: количество строк `daily_answers` не увеличивается; существующая строка и
исходное chatter-сообщение обновляются.

## TC-04: готово и ссылка на результат

1. Выбрать статус `Готово`.
2. Передать тестовую HTTPS-ссылку.

Ожидается: ссылка сохраняется в `daily_answers.result_url` и отображается кликабельной
в chatter задачи.

## TC-05: затруднение и AI

1. Нажать `Есть затруднение` и описать конкретную проблему.
2. Проверить короткий совет или один уточняющий вопрос.

Ожидается: создаются или обновляются `blockers` и `ai_advices`; AI получает только
контекст текущей задачи; совет виден в Telegram и отдельном chatter-сообщении Odoo.

## TC-06: снятие затруднения

1. Нажать `Затруднение решено` сразу или открыть `/blockers` позже.
2. Передать ссылку на решение либо `/skip`.

Ожидается: статус становится `resolved`; ссылка сохраняется; исходное сообщение Odoo
обновляется без нового дубля; прерванный дейли продолжается.

## TC-07: недоступность Odoo

1. Временно указать несуществующий test URL Odoo и пройти один ответ.
2. Вернуть правильный URL и дождаться worker.

Ожидается: ответ остаётся в PostgreSQL, outbox переходит в `retry`, затем в `sent`;
пользовательский текст не теряется.

## TC-08: недельный фокус

1. Отправить `/weekly`.
2. Выбрать несколько задач и подтвердить.
3. Добавить стратегический текст.

Ожидается: создаётся одна `weekly_plans` на пользователя и понедельник текущей недели;
повторное прохождение обновляет её.

## TC-09: PM-команды

1. От PM-аккаунта выполнить `/status`, `/deadlines`, `/digest` и `/digest week`.
2. Выполнить `/remind`.
3. Повторить команду с аккаунта без роли.

Ожидается: PM получает агрегированные данные и адресные напоминания; обычный участник
получает отказ без раскрытия командной информации.

## TC-10: эскалация

1. На тестовой записи выставить `created_at` старше двух дней.
2. Запустить job `blocker_escalations`.

Ожидается: статус становится `escalated`; PM и техлид получают участника, задачу,
описание и AI-совет; повторный job не дублирует уведомление.

## TC-11: новое назначение

1. Дождаться первого тихого снимка `task_cache`.
2. Назначить тестовую задачу пользователю в Odoo.

Ожидается: не позднее чем через минуту приходит название, проект, дедлайн и ссылка;
повторный polling без изменения исполнителей ничего не отправляет.

## Протокол результатов

Для каждого кейса фиксируются дата, commit SHA, результат `PASS/FAIL`, ссылка на
GitHub Actions и обезличенный скриншот. Токены, пароли, API keys, Telegram ID и
персональные тексты затруднений в отчёт не включаются.
